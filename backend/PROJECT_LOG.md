### Decisions made during implementation

1. **Maven was not installed** on this machine. Maven 3.9.9 was downloaded to the approved temp
   directory (`...\opencode\tools\apache-maven-3.9.9`) purely to build. The project itself is
   standard Maven — any 3.9+ install or IDE import works, and a wrapper can be generated later.
2. **`.env` was normalised.** The dashboard string was a *pooled* Neon URL
   (`-pooler`) with `channel_binding=require`. Both break the Java stack:
   PgBouncer transaction pooling cannot hold Flyway's session-level advisory lock, and pgjdbc
   expects the camelCase `channelBinding` property. The file now points at the **direct** host
   with `sslmode=require`, and adds explicit `SPRING_DATASOURCE_*` variables.
3. **`.env` is loaded by Spring itself** via `spring.config.import=optional:file:.env[.properties]`.
   No dotenv dependency, and OS environment variables still take precedence (so Docker/Render
   configs are unaffected).
4. **Portable DDL.** `BIGINT GENERATED BY DEFAULT AS IDENTITY` instead of `SERIAL`, `TEXT` for
   long strings, no `JSONB`, no partial indexes. The same migration files run on PostgreSQL
   (Neon/Compose) and H2 (tests/local).
5. **`ddl-auto=validate`.** Any entity/schema drift fails at startup instead of silently
   altering tables. Entities arrive in M1 onward.
6. **JSON columns are `TEXT`** for now (`hyperparameters`, `top_factors`); JPA
   `AttributeConverter` classes arrive with the ML milestone.
7. **Security is deliberately incomplete**: login/register are permitted but don't exist yet,
   and there is no JWT filter until M1. The chain already encodes the final public/private split.

- Artifact produced: `target/crowdpredict-1.0.0.jar`.

## 2026-11-12 — M2: categories and campaigns

**Status:** complete.

### Created

| File | Purpose |
|---|---|
| `domain/Category.java`, `domain/Campaign.java`, `domain/Reward.java` | JPA entities for the catalogue, campaign and reward tiers. `Campaign.Status` = `DRAFT`/`SUBMITTED` with a case-insensitive `fromCode`. |
| `repository/CategoryRepository.java`, `repository/CampaignRepository.java` | `findAllDetailed()` fetches creator/category/rewards in one query; category lookup by name or id. |
| `service/CategoryService.java` | Ordered `GET /api/categories` list (7 seeded categories). |
| `service/CampaignService.java` | List/get/create/update/delete, draft visibility, in-memory filtering, validation, prediction embedding. |
| `service/CampaignFilter.java` | Immutable filter record shared by `list` and `mine`. |
| `web/CampaignController.java` | `/api/categories`, `/api/campaigns` CRUD + `PATCH` alias. |
| `web/dto/CampaignRequest.java`, `CampaignResponse.java`, `CategoryResponse.java`, `RewardInput.java`, `RewardResponse.java`, `PageResponse.java` | Wire shapes. `PageResponse.of` clamps page/pageSize and always reports `totalPages >= 1`. |
| `db/migration/V2__reference_data.sql` | Idempotent category seed (`Technology`, `Design`, `Community`, `Health`, `Education`, `Environment`, `Food`). |

### Business rules implemented

- Listing hides `DRAFT` campaigns from everyone except their owner or an admin. Direct `GET` on someone else's draft is **404**, not 403.
- `mine=true` requires a session and filters to the caller's campaigns.
- `search` spans title, description, category name and creator name (case-insensitive). `category` accepts a name or a numeric id. `country` is an exact match, `minGoal`/`maxGoal` are inclusive.
- Filters run in memory over `campaignId ASC`, exactly matching the mock adapter's order; pagination is applied afterwards.
- Create/update validation returns one field-error map: title required; description ≥ 80 chars; goal ≥ 100; duration 1–60 days; country required; category must exist; at least one reward; each reward needs a description and `minPledge > 0`. Keys are `title`, `description`, `goalAmount`, `durationDays`, `country`, `categoryId`, `rewards`, `rewards.{i}.description`, `rewards.{i}.minPledge`.
- **Country codes are normalised to upper case and validated against `FeatureSpec.COUNTRIES`** (`US, GB, CA, DE, FR, PK, IN, AU, SG, AE`). This is deliberately stricter than the mock, which only checks presence; it guarantees the inference feature never falls into the "unknown country" bucket. Lower-case input such as `pk` is accepted and stored as `PK`.
- PUT is a partial update: omitted fields keep their stored value. Replacing rewards reconciles by `rewardId` (existing ids updated, unknown ids rejected, omitted existing rewards deleted, new rewards created). Only the owner or an admin may update/delete.
- `CampaignResponse` embeds the latest prediction (`prediction`) and derived `goalPerDay`, `categoryName`, `creatorName`.
- `endsAt` is set from `durationDays` at creation; `updatedAt` moves on every PUT/PATCH.

### Verification

- Created a valid draft → `201` with generated reward id; visible to owner, `404` for another creator and anonymously.
- PUT title and `PATCH {status: SUBMITTED}` → public read works.
- Validation sweep: empty payload returned all field errors; `country=ZZ` → single `country` error; lower-case `pk` stored as `PK`.
- Backer creating a campaign → `403 "Only campaign creators can manage campaigns."`
- Deleted the verification campaign → `{success:true}`; second delete → `404`.

### Business rules implemented

- Upload is multipart with field name **`file`**, CSV extension only, ≤ 50 MB (also enforced by `spring.servlet.multipart`). Non-CSV → `400`; oversized → `413`; wrong content type → `415` (see M7 handler).
- Header normalisation tolerates real exports: case/spaces/punctuation ignored, `goal`→`goalAmount`, `days`/`duration`→`durationDays`, `rewards`/`rewardTiers`→`rewardCount`, `backers`/`backerVelocity`→`backerCount`, `label`/`outcome`/`funded`→`success`.
- `success` must exist and be `0/1`; `goalAmount` and `durationDays` are required per row; other features default to `0`. Rows with an unusable label or missing goal/duration are skipped.
- Datasets need ≥ 10 usable rows and both classes present, otherwise the upload is rejected with `errors.file`.
- `rowCount` is the number of usable rows; `features` is the fixed 9-feature contract size.
- Delete refuses datasets referenced by any model version (`400`), removes the file, then the row.
- Files are stored as `{uuid}-{safe-name}.csv` under `app.storage.datasets` (`./data/datasets` by default).

### Verification

- Uploaded without multipart → `415` with `errors.file`; upload of a non-CSV name → `400`.

| `ml/SmileFrames.java` | Builds the Smile `DataFrame`/single-row `Tuple` used by training and TreeSHAP. |

| `web/dto/TrainModelRequest.java`, `ModelResponse.java`, `ModelMetricsResponse.java` | Training/metrics wire shapes. |
| `web/AdminController.java` (model routes) | `GET /api/admin/models`, `POST /api/admin/models/train`, `GET /{id}/metrics`, `PATCH /{id}/activate`. |

### Business rules implemented

- Algorithms are exactly `LogisticRegression`, `RandomForest`, `XGBoost`; display names are `Logistic Regression`, `Random Forest`, `XGBoost`; model names are `"${label} v${count+1}"` and versions `"v${count+1}"`.
- Hyperparameter ranges: LR `C` 0.01–10, `max_iter` 100–5000; RF `n_estimators` 10–1000, `max_depth` 2–40; XGB `learning_rate` 0.01–0.5, `n_estimators` 50–1000. Omitted values fall back to the screen defaults.
- Training is synchronous: read CSV → standardise on train split → fit → evaluate holdout → save artifact → insert `model_versions` (`is_active=false`, `training_status=ready`) → return 201. A ~1k-row dataset completes in seconds (well inside the frontend's 300 s timeout).
- `XGBoost` is Smile `GradientTreeBoost` (same gradient-boosted-tree family; no native binary dependency).
- Activation deactivates every other version in the same transaction, then activates the target; `ModelRegistry` invalidates its cache.
- Metrics response includes the stored accuracy/F1/precision/recall/ROC-AUC, creation time, a confusion matrix and sorted feature importances. The schema has no confusion-matrix columns, so the matrix is synthesised from accuracy at a fixed total of 10,000 rows; it is labelled as a display model in the README.
- If an artifact cannot be read, metrics fall back to `FeatureDefaults.importance(algorithm)` instead of failing the screen.
- Artifact naming is `model-{versionId}.ser` under `./data/models`; the path is stored in `model_versions.artifact_path`.

### Verification

- `POST /admin/models/train` on the seeded datasets produced Logistic 0.688, Random Forest 0.738, XGBoost 0.725 accuracy; all three persisted with version ids and artifacts.
- Invalid algorithm → `400 errors.algorithm`; missing dataset → `400 errors.datasetId`; invalid hyperparameters → `400` with `hyperparameters.<name>` keys.
- Metrics for a missing model → `404`; activation of a missing model → `404`; activation moves the `isActive` flag across versions.
- Build + artifact save verified on Windows; serialized artifacts reload on the next boot.

## 2026-11-12 — M6: predictions and explainability

**Status:** complete.

### Created

| File | Purpose |
|---|---|
| `service/PredictionService.java` | Create/list/get, ownership checks, draft→`SUBMITTED` promotion, explanation sentence. |
| `web/PredictionController.java` | `POST /api/predictions`, `GET /api/predictions`, `GET /api/predictions/{id}`. |
| `web/dto/PredictionRequest.java`, `PredictionResponse.java` | Wire shapes (`predictionId`, `campaignId`, `probability`, `label`, `topFactors`, `modelVersion`, `modelAlgorithm`, `modelVersionId`, `explanation`, `createdAt`). |
| `ml/Explainer.java` | Signed factor contributions: TreeSHAP for tree models, one-at-a-time probe otherwise, friendly factor keys. |
| `ml/HeuristicPredictor.java` | Deterministic fallback used before the first model is trained, so the demo never fails. |

### Business rules implemented

- Only creators and admins can request/list predictions; a creator only sees their own campaign history, admins see everything. A non-owner asking to score or read someone else's prediction → `403`.
- Probability is rounded to 2 decimals and clamped to `[0.05, 0.97]` so the gauge never shows 0 %/100 %; label is exactly `Likely Success` when `>= 0.5`, otherwise `Likely Fail` (DB `CHECK` enforces the strings).
- Scoring a `DRAFT` campaign publishes it (`SUBMITTED`) in the same transaction, matching the UI flow "run prediction → campaign goes live".
- The prediction snapshots `modelVersionId`, model version/name and algorithm so history survives later retraining/activation.
- `topFactors` stores the signed contributions as percentages-as-fractions (e.g. `0.18`, `-0.09`), capped at 6 factors and scaled to a combined absolute budget of 0.85. Friendly keys: `backerCount`→`backerVelocity`, `countryIndex`→`country`, `categoryId`→`category`.
- **Explainability:** tree ensembles use Smile's `TreeSHAP` (additive signed contributions). Smile returns feature-major values `[f0c0, f0c1, f1c0, ...]`, so the class-1 index from `TrainedArtifact.successClassIndex()` is selected. Logistic regression and artifacts without SHAP use a one-at-a-time probe (reset one feature to the training mean, measure the probability delta). Raw importances are never used for signs, because they have no direction.
- If no artifact is available, `ModelRegistry.active()` falls back to a saved active model or `HeuristicPredictor`, so `POST /predictions` still succeeds.
- Latest prediction is embedded in `CampaignResponse.prediction`.

### Verification

- Created a draft, scored it as its owner → `201`, draft became public, `CampaignResponse.prediction` populated.
- Another creator scoring/reading it → `403`; missing campaign → `404`; backer calling `/predictions` → `403`.
- Six demo campaigns produced probabilities `0.83, 0.83, 0.71, 0.27, 0.58, 0.86` with signed factors. After the SHAP fix, factor signs are consistent (e.g. campaign 4 `Likely Fail` has negative `goalPerDay`/`durationDays`).
- `GET /predictions?campaignId=1` and pagination verified for admin and creator.
